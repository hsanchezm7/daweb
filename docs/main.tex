\section{Introducción}

  Este proyecto se basa en la implementación y desarrollo de un cliente
  ``\textit{frontend}'' basado principalmente en el framework React.js y la
  libraríe de componentes Bootstrap. Dicha interfaz complementa el backend basado
  en microservicios realizado en la asignatura de Arquitectura del Software.

\section{Requisitos}

  Para garantizar la correcta instalación y puesta en marcha del servicio, el
  entorno debe cumplir con los siguientes requisitos previos:

  \begin{itemize}
      \item \textbf{Node.js} (v20.20 o superior): Para ejecutar el cliente. \href{https://nodejs.org/}{Descargar}.
      \item \textbf{Docker}: Para levantar los servicios del servidor. \href{https://www.docker.com/}{Descargar}.
  \end{itemize}

  El resto de las dependencias específicas del proyecto serán descargadas y
  resueltas automáticamente por las herramientas mencionadas durante el proceso
  de instalación.

\section{Instalación y ejecución}

  El proceso de despliegue de la aplicación se divide en dos partes principales:
  los servicios del backend y la interfaz del frontend.

  Los servicios correspondientes al primero están contenerizados para asegurar un
  entorno de ejecución consistente. Dicha infraestructura se despliega y orquesta
  mediante Docker Compose. Para levantar estos servicios, basta con ejecutar el
  siguiente comando desde el directorio \texttt{backend/}:

  \begin{lstlisting}[style=BashStyle]
    $ docker compose up -d
\end{lstlisting}

  Para detener el servidor:

  \begin{lstlisting}[style=BashStyle]
    $ docker compose down
\end{lstlisting}

  Para levantar el cliente (frontend), es necesario, desde su carpeta
  correspondiente \texttt{frontend/}, instalar las dependencias y arrancar en
  modo de desarrollo con:

  \begin{lstlisting}[style=BashStyle]
    $ npm install && npm run dev
\end{lstlisting}

\section{Diseño e implementación de la interfaz}

  \subsection{Sistema de plantillas, páginas, formularios y componentes}

      El diseño de la aplicación se ha conseguido siguiendo un enfoque modular,
      haciendo uso de componentes y \textit{layouts} (plantillas de diseño),
      aprovechando las capacidades de React y React Router.

      Los componentes representan piezas de interfaz independientes y reutilizables,
      como pueden ser el \texttt{Header}, el \texttt{Footer} o el menú lateral
      \texttt{Menu}. Aislar la lógica de estos componentes a ficheros dedicados ha
      facilitado enormemente el desarrollo gracias a la escalabilidad que
      proporciona, y ha resultado vital para el mantenimiento del código.

      Para estructurar las vistas, se han definido diferentes plantillas que actúan
      como envoltorios para las rutas. Por ejemplo, el \texttt{MainLayout} define la
      estructura base con un encabezado, un contenedor central y un pie de página.
      Como cada página que emplee esta plantilla renderiza un componente principal
      distinto, se hace uso del elemento \texttt{<Outlet />} de React Router.

      Para el panel, se han podido juntas las vistas de administración de usuario
      gracias a definir un \texttt{PanelLayout}. Este layout divide la vista en dos
      columnas: una barra lateral fija que contiene el componente \texttt{Menu} y una
      sección principal donde se carga el contenido específico mediante su propio
      \texttt{<Outlet />}.

  \subsection{Análisis global de las vistas de la aplicación con React Router}

      La navegación de la aplicación en el lado del cliente se gestiona utilizando
      \textbf{React Router}. Esta biblioteca permite definir rutas de distinta forma
      (\textit{Data}, \textit{Framework} y \textit{Declarative}). A pesar de sus
      limitaciones frente al resto, se ha escogido el enfoque declarativo debido a su
      sencillez y porque es el usado en las prácticas.

      De esta forma, podemos asociar cada URL de navegación con la jerarquía de
      componentes que debe renderizarse, indicando, en una misma porción de código,
      todo lo que necesitamos para la correcta navegación.

      En el componente principal, se emplea el contenedor \texttt{<Routes>} para
      agrupar todas las rutas de la aplicación, anidándolas bajo distintos
      envoltorios (plantillas) junto con reglas de autorización:

      \begin{lstlisting}[style=ReactStyle]
    // App.jsx
    <Routes>
      <Route element={<MainLayout />}>
        <Route path="/" element={<Inicio />} />
        <Route path="/buscar" element={<Buscar />} />
      </Route>

      <Route element={<AuthLayout />}>
        <Route path="/login" element={<Login />} />
        <Route path="/signup" element={<Register />} />
      </Route>
      ...
    </Routes>
\end{lstlisting}

      Como se observa en el código, el enrutamiento se organiza lógicamente
      estructurando las distintas páginas como componentes hijos de su plantilla
      correspondiente. A continuación muestra como se agrupan cada una de las vistas:

      % TODO: Añadir las rutas que faltan
      \begin{itemize}
          \item \textbf{\texttt{MainLayout}}: Plantilla base con encabezado y pie de página. Engloba:
                \begin{itemize}
                    \item \texttt{/}: Vista principal de aterrizaje (\texttt{Inicio}).

  \subsection{Autenticación y autorización}

      Las aplicaciones React mantienen el estado de sus componentes únicamente
      mientras la aplicación permanece en ejecución. Cuando la página se recarga o el
      usuario inicia una nueva sesión en el navegador, dicho estado se pierde. Por
      este motivo, las aplicaciones que requieren autenticación deben utilizar
      mecanismos de almacenamiento persistente que permitan conservar la información
      de sesión. En React existen, principalmente, tres zonas en las que guardar
      información:

      \begin{itemize}
          \item \textbf{In-memory state}: Guarda el estado de los componentes. Se pierde al renderizar otros componentes, por ejemplo, refrescando la página.
          \item \textbf{Local Storage}: Es un sistema de información persistente del navegador. Guarda información entre las distintas sesiones.
          \item \textbf{Cookies}: Son pequeños fragmentos de información almacenados por el navegador. A diferencia del anterior, se envían automáticamente al servidor en cada petición HTTP.
      \end{itemize}

      Una primera idea sería tener un token JWT suministrado por el backend al
      acceder a \texttt{/login}. Este token no se podría almacenar en memoria, ya que
      se perdería, por lo que habría que almacenarlo en el Local Storage del
      navegador. Este enfoque conlleva diversos problemas de seguridad, ya que el
      \textit{Local Storage} es accesible directamente desde JavaScript. Esto implica
      que, en caso de una vulnerabilidad de tipo \textbf{\textit{Cross-Site
              Scripting} (XSS)}, un atacante podría obtener el token y suplantar la identidad
      del usuario. Por este motivo, almacenar tokens de autenticación en el navegador
      sin protección adicional no es una buena práctica.

      Una alternativa más robusta consistiría en el uso de una \texttt{cookie}
      configurada con el atributo \texttt{HttpOnly}, que bloquea el acceso de
      JavaScript y soluciona el problema mencionado. Esta opción es la recomendada
      por la asignatura de Arquitectura del Software. Pero presenta un problema
      evidente: durante el ciclo de vida de la cookie, estamos confiando plenamente
      en el usuario. Si la duración de vida es corta, implementaríamos un mecanismo
      para actualizar el token con un endpoint \texttt{/refresh}, pero nunca
      llegaríamos a volver a solicitar las credenciales al usuario. Si la duración de
      vida es larga, tendríamos que confiar en el usuario durante dicho período de
      tiempo. Guardar las credenciales del usuario de forma persistente tampoco es
      una opción viable. Además, somos vulnerables a un segundo tipo de ataque,
      \textbf{\textit{Cross-Site Request Forgery} (CSRF)}, pues estamos enviando la
      cookie en cada petición.

      En la actualidad, existe una solución híbrida que combina ambos conceptos para
      equilibrar la protección contra ataques XSS y CSRF con la flexibilidad que
      exige una API moderna. Dicho estándar propone un enfoque con dos tokens:

      \begin{itemize}
          \item \textbf{Access Token}: De corta duración (10 o 15 minutos), es generado por el backend al iniciar sesión. El cliente (en nuestro caso, la aplicación React) almacena este token únicamente en memoria y lo envía en la cabecera \texttt{Authorization: Bearer <token>} en cada petición a la API. Al no estar en el almacenamiento persistente, se la exposición frente a un ataque XSS, y al no ser una cookie, es inmune al CSRF.

          \item \textbf{Refresh Token}: De larga duración (unos 7 días), también es generado por el backend y establecido al iniciar sesión. Cuando el token de acceso expira y se pierde de la memoria, el cliente realiza una petición a \texttt{/refresh} para renovar dicho token.
      \end{itemize}

      En el lado del cliente, se ha desarrollado un componente interceptor
      \texttt{RequireAuth}, que envuelve las rutas protegidas y verifica si el
      usuario autenticado posee al menos uno de los roles permitidos
      (\texttt{allowedRoles}) especificados en la definición del enrutador de React
      Router. Si el usuario cuenta con los permisos necesarios, se renderiza la vista
      solicitada (componente \texttt{<Outlet />}). En caso de tener los permisos de
      rol necesarios, se le redirige a \texttt{/unauthorized}. Si directamente, el
      usuario no estaba ``\textit{logueado}'', se le redirige a la vista para iniciar
      sesión.

      \begin{lstlisting}[style=ReactStyle]
    // RequireAuth.jsx
    const RequireAuth = ({ allowedRoles }) => {
      const { auth } = useAuth();
      const location = useLocation();

      return auth?.roles?.find((role) => allowedRoles?.includes(role)) ? (
        <Outlet />
      ) : auth?.usuario ? (
        <Navigate to="/unauthorized" state={{ from: location }} replace />
      ) : (
        <Navigate to="/login" state={{ from: location }} replace />
      );
    };
\end{lstlisting}

      \subsubsection{Gestión y ciclo de vida de los tokens}

          La sincronización de las peticiones HTTP privadas y la actualización de las
          credenciales expiradas se lleva a cabo mediante interceptores de Axios y hooks
          personalizados:

          \begin{itemize}
              \item \textbf{Hook \texttt{useRefreshToken}}: Expone una función para solicitar la renovación del token de acceso. Realiza una petición al endpoint de renovación (\texttt{/refresh}), el cual lee el Refresh Token, enviado automáticamente por el navegador.
              \item \textbf{Hook \texttt{useApiPrivate}}: Configura una instancia de Axios dedicada a realizar peticiones HTTP autenticadas. Esta instancia incluye dos interceptores:
                    \begin{itemize}
                        \item \textbf{Interceptor de petición (\textit{Request Interceptor})}: Es necesario para inyectar de forma automática la cabecera \texttt{Authorization: Bearer <token>} con el Access Token actual antes de que la petición salga al servidor.
                        \item \textbf{Interceptor de respuesta (\textit{Response Interceptor})}: Es posible que el Access Token haya caducado, pues su \textit{lifespan} es bastante corto. El backend informará con un error HTTP \texttt{401 Unauthorized}. Es aquí donde éste interceptor actúa, iniciando el proceso de renovación llamando al hook definido anteriormente como \texttt{useRefreshToken}, actualizando la cabecera de la petición original con el nuevo Access Token y volviéndola a intentar (una única vez).
                    \end{itemize}
          \end{itemize}

          Se puede dar el caso en el que, o bien por caducidad o por invalidez, el
          Refresh Token almacenado en la cookie del navegador ya no sea válido. En este
          caso, el frontend debe darse cuenta de que el usuario ha perdido su sesión
          persistente, y que debe volver a identificarse con sus credenciales en el
          servidor. El interceptor analiza la respuesta ante un intento de renovación, y
          redirige al usuario forzosamente al formulario de \texttt{/login} en caso de un
          Refresh Token inválido.

          \begin{lstlisting}[style=ReactStyle]
    // useApiPrivate.jsx
    const requestId = instancePrivate.interceptors.request.use(
      (config) => {
        config.headers['Authorization'] ??= `Bearer ${authRef.current?.accessToken}`;
        return config;
      },
      (error) => Promise.reject(error)
    );

    const responseId = instancePrivate.interceptors.response.use(
      (response) => response,
      async (error) => {
        const prevReq = error?.config;

        if (error?.response?.status === 401 && !prevReq?.sent) {
          prevReq.sent = true; // un único intento

          try {
            refreshPromise ??= refreshRef.current().finally(() => refreshPromise = null);
            prevReq.headers['Authorization'] = `Bearer ${await refreshPromise}`;
            return instancePrivate(prevReq);
          } catch { // limpiar auth y redirigir a /login
            setAuth({}); navigate('/login', { replace: true });
          }
        }

        return Promise.reject(error);
      }
    );
\end{lstlisting}

  \subsection{Otros aspectos y tecnologías}

      El desarrollo de este proyecto no hubiese sido posible sin el uso de algunas
      tecnologías y técnicas que han permitido complementar el cliente y mejorar la
      experiencia de usuario.

      La implementación de la autenticación se ha realizado en base al
      \href{https://www.youtube.com/playlist?list=PL0Zuz27SZ-6PRCpm9clX0WiBEMB70FWwd}{curso
          de gestión de accesoy autenticación} de Dave Gray en Youtube.

      A medida que la jerarquía de carpetas se vuelve más profunda, vimos que una
      buena práctica en estos entornos es usar \textbf{rutas absolutas} en vez de
      rutas relativas~\cite{salteadorneo_alias}. Para implementarlo, se han
      configurado rutas absolutas mediante el uso de alias (\texttt{@/}). Esto ha
      requerido configurar Vite en el archivo \texttt{vite.config.js}, ya que es el
      \textit{bundler} empleado, y definir la resolución de los distintos directorios
      en \texttt{jsconfig.json}, aunque este último es solo para el analizador
      estático ESLint.

      También se han usado librerías externas de código abierto para mejorar la
      experiencia de usuario. Algunos ejemplos son los componentes
      \textbf{DatePicker} de \href{https://getdatepicker.com/}{Tempus Dominus} o
      \textbf{International Telephone Input} para números de teléfono
      \href{https://getdatepicker.com/}{Intl-Tel-Input}. Estos componentes han
      resultado un acierto para facilitar la validación de dichos campos e introducir
      restricciones que, de otras formas, habría que configurar manualmente.

      Para algunos campos de selección de los formularios, como las categorías, se ha
      importado el componente \textbf{Typeahead} de
      \href{https://getdatepicker.com/}{React Bootstrap Typeahead}. Esta librería
      profundiza el input de selección ofreciendo búsquedas, renderizado personaliado
      y otras funciones que no se han utilizado como paginación.

      La animación ``\textit{3D tilt}'' de las cartas de productos está fuertemente
      inspirada en la implementación de Jeroen Reumkens de su blog
      \href{https://www.frontend.fyi/tutorials/css-3d-perspective-animations}{Frontend.yi}.
      Gracias a React, no necesitamos de librerías externas pesadas de 3D como
      Three.js.

      Los carruseles de productos se han implementado con la librería
      \href{https://swiperjs.com/}{Swiper.js}. Aunque Bootstrap ofrece esta función,
      únicamente permite slides completos. Esto obligaría a actualizar todos los
      productos en cada slide (no muy UX-\textit{friendly}). Con Swiper y React
      podemos definir un carrusel de forma sencilla y usar módulos de navegación y
      \textit{autoplay}, controlar la velocidad, los breakpoints de responsiveness,
      etc.
